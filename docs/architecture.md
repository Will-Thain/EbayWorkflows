# System Architecture

## High-Level Architecture

The application is a local CLI orchestration system with a PostgreSQL backing store and phase-oriented workers. A **desktop GUI** (PySide6 / Qt 6) is specified for operator review, job control, and scheduling; see `gui-application.md`.

Core components:

1. **CLI Entrypoint**
   - receives workflow command and options
   - creates a workflow run record
   - dispatches phase executors

2. **Workflow Engine**
   - executes phases in configured order
   - persists step checkpoints and errors
   - supports resume/retry semantics

3. **Connectors**
   - eBay connector for listing retrieval
   - Scryfall connector for card reference matching
   - Cardmarket connector for pricing enrichment

4. **Image Pipeline** (see `card-recognition-architecture.md`)
   - image downloader/cache manager
   - card region detector (OpenCV contours)
   - align + zone crop extractor (name, art, bottom, symbol, mana)
   - OCR and template/symbol matchers on zone strips
   - embedding generator (OpenCLIP art-zone query; FAISS corpus)
   - evidence normalizer and `image_verified` gate

5. **Scoring Engine**
   - EV calculation
   - confidence calculation
   - ranking output generator

6. **Storage Layer**
   - PostgreSQL repositories and migrations
   - optional local filesystem cache for images/artifacts

7. **Desktop GUI (PySide6)**
   - `QProcess` orchestration of CLI phases (start/stop, log tail)
   - Opportunities viewer (ranked listings, favourites, image preview)
   - Database browser (curated read-only queries)
   - schedule editor backed by `scheduled_jobs` (see `gui-application.md`)
   - must not import torch/OpenCLIP/OCR; heavy phases stay in child CLI processes

## Module Boundaries

- `cli`: command parsing and output formatting
- `gui`: PySide6 application (`qt_app`, Qt models, `QProcess` job runner; shared `favorites`, `workflow_catalog`)
- `workflows`: phase graph, orchestration, status transitions
- `integrations`: typed clients for eBay/Scryfall/Cardmarket
- `image`: download, OpenCV preprocessing, detection, OCR
- `matching`: OpenCLIP embedding search, FAISS retrieval, and evidence-based entity resolution
- `scoring`: EV/confidence formulas and ranking logic
- `db`: schema migration and data access abstractions
- `common`: config, logging, error model, utility types

## Workflow Execution Model

- **Run**: one invocation with parameters and time window
- **Step**: one phase execution within a run
- **Artifact**: structured outputs generated by a step
- **Resume**: rerun only failed/incomplete steps with same run config

## CV and Matching Stack

Propose-then-confirm design (full detail: `card-recognition-architecture.md`):

- `OpenCV` — region detection, alignment, zone crops
- `OpenCLIP` + `FAISS` — propose Scryfall candidates from art-zone embeddings
- `Tesseract` (baseline) / `PaddleOCR` (planned) — zone OCR for confirmation
- `set_symbol_match` + `mana_cost` — non-OCR zone confirmation signals
- `RapidFuzz` — name reconciliation against Scryfall records
- Optional future: Milo/CollectorVision catalog as embedder proposer (no zone replacement)

## Error Handling Strategy

- classify errors as transient vs permanent
- retry transient integration/network failures with backoff
- mark permanent record-level failures while allowing batch progress
- keep raw error payloads for diagnostics with sensitive redaction

## Observability

- structured logs with `run_id`, `step_name`, `listing_id`
- database step status records with timestamps and counters
- optional run report export (JSON/CSV) for post-run analysis

## Security and Secrets

- credentials only from environment variables or secure local secret store
- least-privilege database role for app runtime
- no secret material persisted in logs or checked into source control
